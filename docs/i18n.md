## i18n content resolution (`loadMessages`)

This is the full reference the README's
["i18n content resolution (`loadMessages`)"](../README.md#i18n-content-resolution-loadmessages)
section points to — the content-resolution half of i18n, given a `(lang, population)` pair (from
`langPreHandler`'s own `:lang` route segment and `populationGuard`'s own `ctx.population` — see
[`docs/middleware.md`](./middleware.md)), resolves the actual message catalog to render.

### Configuring and reading a catalog

```ts
// space.app.ts
export default defineSpaceApp({
  name: 'storefront',
  messagesDir: './messages',
  clientBuildDir: './.dist/client',
})
```

`clientBuildDir` isn't just for the client bundle here — it's also where `zanix space build` writes
this catalog's own COMPILED form (see "Compilation lands in its own directory" below). Without it
declared, production falls back to reading `messagesDir` live — the same raw, uncompiled ICU strings
`znx space dev` always reads, never AST.

```
messages/
  en/
    index.json                 # base catalog segment: { "home/title": "Welcome" }
    iam.json                   # another base segment, merged with index.json: { "login/...": ... }
    profile.json               # segments are namespaced/disjoint by convention, not enforced
    populations/
      zanix.json                # override: only the keys that differ from the merged base
  es/
    index.json
    iam.json
    profile.json
```

The base catalog is every `.json` file directly under `{lang}/` — `index.json` is the conventional
single-file default, not a hardcoded requirement. Splitting a large catalog into feature-segmented
files (`iam.json`, `profile.json`, `chat.json`, ...) is expected and fully supported; see
"Segmenting a large base catalog" below for the merge details.

```tsx
import { loadMessages } from '@zanix/space'
import { IntlProvider, useIntl } from '@zanix/space-ui'

loader = async (ctx: { params: { lang: string }; population?: string }) => ({
  lang: ctx.params.lang,
  messages: await loadMessages({ lang: ctx.params.lang, population: ctx.population }),
})
// NEVER interpolate `messages[key]` directly — see "Formatting stays out of this package" below
// for why (a compiled catalog value is precompiled AST, not a string) and the safe pattern.
component = ({ lang, messages }) => (
  <IntlProvider locale={lang} messages={messages}>
    <Home />
  </IntlProvider>
)
function Home() {
  const { formatMessage } = useIntl()
  return <h1>{formatMessage('home/title')}</h1>
}
```

Reads every `.json` file directly under `{messagesDir}/{lang}/` (the base catalog segments — see
below) and, when `population` is given, `{messagesDir}/{lang}/populations/{population}.json` (an
override), then shallow-merges everything: every base segment first, then the override on top —
`{ ...segment1, ...segment2, ..., ...override }`. This is only correct because catalogs are
**flat**, namespaced-string-key objects — never nested; a nested shape would silently lose sibling
keys on any collision instead of merging.

A missing override file is the normal case (not every population overrides every language) and
resolves silently to the merged base catalog. Finding no base segment file at all (an empty or
missing `{lang}/` directory) logs a warning and resolves to `{}` — language-level fallback
(redirecting to `defaultLang`) is `langPreHandler`'s job, not this function's; by the time a
`loader` calls this, the URL's `lang` is already valid. A malformed file (invalid JSON, or not a
flat object) logs an error and is skipped — every base segment and the override are each read and
validated **independently**, so one broken segment degrades the merge to every other valid segment
plus the override, never discarding otherwise-valid content elsewhere in the catalog.

### Segmenting a large base catalog

A catalog with a few hundred keys in one `index.json` gets unwieldy fast. Split it into as many
`.json` files as makes sense, directly under `{lang}/` — by feature, by owning package, whatever
convention fits the app:

```
messages/
  en/
    index.json      # shared/generic strings — home, legal, errors, not-found, ...
    iam.json         # login, logout, password recovery, TOTP enrollment, ...
    profile.json     # profile editing
    chat.json        # chat/messaging
```

Every file found is merged (`{ ...index, ...iam, ...profile, ...chat }`, filename-sorted for
determinism) into one base catalog before the population override is applied — from a `loader`'s own
perspective, `loadMessages()`'s return value looks identical whether the app used one file or ten.
Segments are expected to be namespaced/disjoint (`'profile/name'`, `'chat/heading'`, ...) — a key
collision between two segment files is resolved by filename-sort order, but relying on that is not
recommended; keep segment key spaces disjoint the same way the top-level namespace convention
(`'home/title'`, `'profile/name'`) already keeps unrelated features from colliding within one file.
`populations/` stays reserved for overrides — a file directly inside it is never treated as a base
segment, however it's named.

`zanix space build` needs no configuration change to compile a segmented catalog: its own compiler
already walks every `.json` file under `messagesDir` recursively, not just `index.json` — segmenting
the base catalog was already supported on the build side before `loadMessages()` itself could read
it back.

### Error and not-found pages

`error.tsx` and `not-found.tsx` (see [`docs/routing.md`](./routing.md)) never need to call
`loadMessages` themselves — when the app declares `messagesDir`, both receive an already-resolved
`messages` catalog as a prop, on the same `IntlProvider`/`useIntl` contract every other page uses:

```tsx
// routes/error.tsx
import type { ErrorBoundaryProps } from '@zanix/space'
import { IntlProvider, useIntl } from '@zanix/space-ui'

export default function ErrorPage({ error, messages }: ErrorBoundaryProps) {
  return (
    <IntlProvider locale='en' messages={messages}>
      <Content error={error} />
    </IntlProvider>
  )
}
```

```tsx
// routes/not-found.tsx
import type { NotFoundProps } from '@zanix/space'

export default function NotFound({ lang, messages }: NotFoundProps) {/* ... */}
```

The two resolve on different schedules, matching how each is actually reached:

- **`ErrorBoundaryProps.messages`** resolves eagerly, once per request, regardless of whether the
  segment actually fails — the wrapper markup a render-phase error recovers from is written before
  React/Preact knows whether the segment will throw, the same reason a segment's `params` is already
  resolved unconditionally. `loadMessages`'s own per-`lang:population` cache keeps this free for the
  overwhelmingly common case where nothing fails.
- **`NotFoundProps.messages`**, and the loader-thrown `HttpError('NOT_FOUND')` recovery path, both
  resolve lazily — only once a 404 is already confirmed, inside the same function that renders it.

Neither ever requires a `messages.tsx`/`loader` of its own to opt in — declaring `messagesDir` is
the only thing that turns this on; an app without it gets `messages: undefined` in both props, at no
extra cost.

### Resolving without a `lang` route param

A page under real `/[lang]/...` routing reads `ctx.params.lang` directly. An app with `messagesDir`
but no `langPreHandler` — a single implicit content variant, no URL-based i18n at all — has no
`:lang` route param to read from at all, for a normal page's own `loader`, for `error.tsx`, or for
`not-found.tsx` alike. `@zanix/space` exports `DEFAULT_IMPLICIT_LANG` (`'default'`) for exactly this
case — a shared naming convention, not a value `loadMessages` itself special-cases:

```ts
import { DEFAULT_IMPLICIT_LANG, loadMessages } from '@zanix/space'

loader = (ctx) => ({
  messages: await loadMessages({ lang: DEFAULT_IMPLICIT_LANG, population: ctx.population }),
})
```

```
messages/
  default/
    index.json                 # this app's one and only content variant
    populations/
      zanix.json
```

The folder is named `default`, never a real language code like `'en'` — the app has no
`langPreHandler` resolving an actual language, so naming the folder after one would misleadingly
claim the content is specifically English rather than "whatever this app's only variant happens to
be." `error.tsx`/`not-found.tsx`'s own `messages` resolution (above) falls back to
`DEFAULT_IMPLICIT_LANG` the same way, whenever no real `lang` was resolved for the request — so all
three (a page's own `loader`, `error.tsx`, `not-found.tsx`) agree on one catalog folder without any
of them special-casing the other two. `@zanix/cli`'s `zanix new space --template population` (as
opposed to `--template population-lang`, which has real `/[lang]/...` routing) scaffolds exactly
this shape.

### Caching

Cached for the process lifetime, keyed by `${lang}:${population ?? ''}`. Concurrent calls for the
same not-yet-cached key share a single in-flight resolution instead of each redoing the same file
I/O — this de-duplication still applies under `znx space dev` too (see below).

**The cache is bypassed entirely under `znx space dev`** — editing a message file while the dev
server is running is reflected on the very next request, no restart needed, the same live-edit
experience `assetsDir` already gives. Automatic, driven by the same dev-mode flag every other Space
dev-time behavior already reads — not an opt-in flag a caller has to remember to pass.

`messagesDir` accepts an array too — same first-match-wins host-composition precedent as
`routesDir`/`assetsDir`, resolved independently for the base file and the override file.

### Compilation lands in its own directory — `messagesDir` is never rewritten

`@zanix/cli`'s `zanix space build` compiles `messagesDir`'s ICU strings to AST and writes the result
to `{clientBuildDir}/messages/{rootIndex}/...` — **never back into `messagesDir` itself.** A
developer's own hand-authored catalog stays untouched by an ordinary local build, the same "compiled
output lives in its own directory" contract `clientBuildDir` already has for the client bundle.

This is also why `loadMessages()`'s return value isn't always the same shape: in production, once
`clientBuildDir` is configured, it reads the COMPILED catalog from there (`getMessagesBuildDir()`) —
`CompiledMessageNode[]` values (structurally mirroring `@formatjs/icu-messageformat-parser`'s own
`MessageFormatElement`, never importing it — `@zanix/space` never depends on FormatJS/ICU, even as a
type), not strings. Under `znx space dev`, which never runs the compiler at all, it reads
`messagesDir` LIVE instead — raw, uncompiled ICU strings. A catalog may freely mix already-compiled
and not-yet-compiled values across keys either way; both resolve identically through
`IntlProvider`/`useIntl` below — never interpolate `messages[key]` directly, or a production build
(real AST, not a string) crashes ("Objects are not valid as a React child") where dev (always a raw
string) looked fine.

**Deliberately deferred, not implemented here**: a secondary "lazy content" tier fetched after first
paint — a client-side fetch, over HTTP, after hydration. That pattern solves a problem specific to a
CSR-first app bolting SSR on; `@zanix/space` is SSR-first, so a page's `loader` already resolves
(and embeds in the initial serialized state) whatever it calls `loadMessages()` for; there's no
post-hydration gap to fill the same way. If a real page ever needs to defer a genuinely large,
non-critical message subset, a Comet fetching its own subset on hydration is the natural fit — not a
bespoke fetch layer.

### Formatting stays out of this package

No `react-intl` (or any formatting library) coupling anywhere in this resolution path — it returns
whatever is on disk, a raw ICU string or a precompiled AST value, never formatted. Formatting
(plurals, dates, ICU) is entirely the consuming app's own concern.

**`Messages` is opaque on purpose.** `loadMessages()` never inspects what a catalog's values
actually are — a string, or a precompiled AST — it only reads, merges and caches whatever JSON is on
disk. That's what makes the rest of this pipeline possible without `@zanix/space` itself ever
depending on ICU/FormatJS:

- `@zanix/cli`'s `zanix space build` compiles a configured `messagesDir`'s ICU strings into AST —
  see "Compilation lands in its own directory" above for exactly where, and that package's own
  `docs/space.md` for the compiler itself.
- `@zanix/space-ui`'s `IntlProvider`/`useIntl`/`createFormatter` (React and Preact, independent
  bindings, never `preact/compat`) is what actually formats a message — wrapping `@formatjs/intl`'s
  own `createIntl()`. This is the ONE package in this stack that depends on FormatJS at all:

  ```tsx
  import { IntlProvider, useIntl } from '@zanix/space-ui' // or '@zanix/space-ui/preact'

  function Home() {
    const { formatMessage } = useIntl()
    return <h1>{formatMessage('home/title')}</h1>
  }

  // `lang`/`messages` both come from `loader`'s own return value — see the snippet under
  // "Configuring and reading a catalog" above for the full `loader` this destructures.
  component = ({ lang, messages }) => (
    <IntlProvider locale={lang} messages={messages}>
      <Home />
    </IntlProvider>
  )
  ```

`znx space dev` never runs the compiler — `loadMessages()`'s own dev-mode cache bypass (above)
already means an edited message file is reflected on the very next request, and `space-ui`'s
formatter accepts a raw ICU string exactly as it accepts precompiled AST, so there is nothing dev
mode needs to compile.
